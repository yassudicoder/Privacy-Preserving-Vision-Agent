Slide 2 — Proposed Solution

Four boxes, exactly like the reference deck. This is the slide that has to land the idea in twenty seconds.

SLIDE 2
Current ProblemsProposed Solution
  • AI browser agents upload your whole screen to a cloud
  • Passwords, IDs and card numbers leave the device
  • A screenshot leaks what redacted text does not
  • "We don't store your data" is a promise, not a proof
  • A hostile page can hijack the agent by prompt injection
  • Agents click freely, with no bounded authority
  • Whole datasets are pasted into prompts — costly and wrong
  • Local vision model reads the screen on-device
  • PII detected and redacted before anything leaves
  • Text and pixels redacted to the same standard
  • Two fail-closed egress gates verify every payload
  • Page content is typed as data, never as instruction
  • Server returns one action; client validates and executes
  • Statistics computed locally — ~40 numbers, not 150,000 tokens
Problems AddressedUnique Value Proposition
  • Zero raw PII transmission, enforced structurally
  • Screenshot leakage closed by pixel redaction
  • Prompt injection blocked at the type level
  • Unbounded agent authority replaced by a validated allowlist
  • Vendor lock-in removed — four interchangeable backends
  • Token cost cut by computing on-device
  • Privacy claims made auditable, not asserted
  • Privacy is a type, not a policy — compiler-enforced
  • Runs fully offline: on-device backend needs no network
  • Same boundary for every backend — byte-identical payloads
  • Per-step privacy receipt: no line may be a constant
  • 232 KB vision model at 30.3 ms — runs on any laptop
  • Cross-browser MV3: Chrome and Firefox from one source
  • 1,133 tests, including type-level and architecture tests

Speaker Notes

SlideWhat to say
1. Title"We built a browser agent for ISRO problem statement SIH26171. The one-line version: every other AI browser agent asks you to trust that it deletes your data. Ours never receives it."
2. Solution"Today, an AI agent that reads your screen uploads your screen. Passwords, Aadhaar numbers, card details — all of it. We move the eye onto the device. A local model reads the page, personal data is removed before anything leaves, and only sanitised context reaches the planner, which returns exactly one action."
3. Technical"One TypeScript codebase builds a Manifest V3 extension for both Chrome and Firefox. On-device we run OpenCV YuNet through ONNX Runtime Web on WebGPU — 232 kilobytes, 30 milliseconds. The server is a thin Node process that speaks one OpenAI-compatible interface, so Gemini, OpenAI and a local Ollama are all the same code path."
4. Feasibility"The hard parts were platform ones. Chrome's service worker has no DOM, so the model lives in an offscreen document. Firefox has no offscreen API at all, so there are two hosts behind one interface. And we found two quadratics on large pages — a thousand-row table took six minutes to redact. It now takes 367 milliseconds."
5. Impact"For ISRO this means AI assistance on screens that legally cannot leave the building. For everyone else it means the privacy claim is checkable: the extension shows you, on every step, exactly what was redacted and exactly what was sent."
6. References"The vision model is the published YuNet detector; the runtime is ONNX Runtime Web. Our prompt-injection defences follow the OWASP LLM Top 10, and the redaction model follows NIST SP 800-122."

Design Notes

  • Keep the two-column layout from the reference deck — Challenge/Approach and Problem/Solution read far better side by side than as one long list.
  • Put a number on every slide. 232 KB, 30.3 ms, 1,133 tests, 1,032×. Judges remember figures, not adjectives.
  • Slide 3 wants the logo grid, grouped by layer, not one long row.
  • Don't claim more than the repo supports. Say "verified in Chrome" only for the full loop on a real page, which is verified. The local vision model has run in a browser; the 100,000-row timings are from Node with jsdom, not from a browser.
